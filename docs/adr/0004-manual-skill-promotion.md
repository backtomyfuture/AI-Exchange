# Manually promote discovered skills

Skill discovery produces Discovered Skill Candidates only: it must never write directly to `skills_registry` or generate executable `handler.py`, and `--auto-confirm` must not create a production rule. Time-Split Validation discovers a candidate from the earliest 80% of Historical Email, then replays it on the newest 20% and shows matches, observed reply rate, and examples without an automatic pass threshold. Candidate Review shows every field that would become active—triggers, priority, reply requirement, tone, action, and fixed recipients—and lets the operator edit them. Discovery may propose a forward action and fixed recipient from historical evidence so that more useful rules can be surfaced, but the operator confirms or edits that Proposed Forward Target in the conversation. The operator's explicit selection there is the promotion action; the conversation workflow invokes the confirmation mode of the same discovery tool rather than exposing a separately named promotion CLI. If the target skill ID already exists, promotion stops and shows a Skill Promotion Conflict rather than overwriting or merging the existing rule. A promoted rule is loaded only at a planned service restart, not by hot reload. An enabled rule only prepares the editable, approved action and never sends email. This chooses human control over unattended automation because an incorrect inference from historical email would change current routing, priority, reply, or forwarding decisions.
